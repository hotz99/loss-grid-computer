\section{RELATED WORK}\label{related-work}

Single-machine loss-grid optimization intersects loss-landscape
visualization, adaptive loss-grid sampling, heterogeneous
CPU/GPU scheduling, and autotune-and-cache patterns.

\subsection{Loss-landscape visualization and
analytics}\label{rw-losslandscape}

Goodfellow et al.~\cite{goodfellow2015qualitative} introduced
1D linear interpolation between parameter points to
qualitatively characterize neural-network optimization
trajectories. Li et al.~\cite{li2018losslandscape} extended this
to a 2D loss grid with filter-normalized perturbation directions,
the algorithm taken here as the baseline; the official
implementation~\cite{goldstein_loss_landscape_repo} runs it under
MPI on a multi-node cluster. LossLens~\cite{xie2025losslens,losslens_repo}
assembled landscape diagnostics into a visual-analytics
workflow over multiple checkpoints, the interactive use case
that motivates the single-machine constraint here.

\subsection{Adaptive and progressive loss-grid
sampling}\label{rw-adaptive-sampling}

An orthogonal line of work to our thesis replaces the canonical full grid with an
adaptive sampler that evaluates loss only at points predicted
to carry visual information. Prakash, Wang, and Balestriero
apply this to loss-landscape visualization directly, replacing
regular $\alpha,\beta$ sampling with an adaptive algorithm
focused on ``interesting'' regions and comparing it against a
GradVis-style baseline and a vectorized uniform
sampler~\cite{prakash2024adaptive}. Their reported outcome is
mixed: adaptive sampling beats the GradVis-style baseline but
loses to the vectorized uniform sampler due to selection
overhead, and their user-preference comparison is
inconclusive~\cite{prakash2024adaptive}. Our thesis focuses
on optimizing \emph{how} the canonical grid is computed rather
than \emph{what} is sampled. The two directions are
complementary and composable, but composition is out of scope.

\subsection{Heterogeneous CPU/GPU task
scheduling}\label{rw-scheduling}

Task-parallel heterogeneous scheduling assigns whole
independent tasks across devices.
StarPU~\cite{augonnet2011starpu} is the canonical
heterocompute scheduling system, supporting a class of
policies including HEFT-style priority models, work-stealing,
and history-based performance models. This thesis uses the
simpler dynamic self-scheduling variant of that class,
originating with Polychronopoulos and
Kuck~\cite{polychronopoulos1987gss}: idle workers poll a
shared queue and claim one task at a time, with no per-device
performance model required. The simpler variant is sufficient
because loss-grid is embarrassingly parallel with uniform
per-task work, removing the load-imbalance and
heterogeneous-task-cost problems that motivate the richer
StarPU policies. Gallet and
Gowanlock~\cite{gallet2021heterogeneous} provide the
applicability-side counterpart for a CPU--GPU epsilon grid
join, identifying the CPU/GPU throughput ratio as the core
variable that determines whether heterogeneous execution
beats device-only: static and dynamic partitioning yield a
speedup over GPU-only execution only above a workload-dependent
ratio threshold, and regress below it. This thesis inherits
the variable; the threshold itself is workload-specific.

A complementary axis splits a single computation across
devices, with per-device stages exchanging intermediate data
along a pipeline. OpenVINO's HETERO execution mode is a
production example at the intersection of heterogeneous
compute and ML inference~\cite{openvino_hetero}: with
pipeline-parallel \texttt{model\_distribution\_policy}, the
inference model is divided into stages, each stage is assigned
to a device, and the output of one stage is fed as input to
the next. This makes it closer to this thesis's problem domain
than generic heterogeneous-compute scheduling alone: both
execute neural-network inference on mixed devices. Where the
task-parallel axis exploits inter-task independence,
model-parallel heterogeneous execution exploits intra-task
phase boundaries between parts of one computation that suit
different devices.

\subsection{Autotune-and-cache patterns}\label{rw-autotuning}

ATLAS~\cite{whaley1998atlas} introduces an
autotune-and-cache pattern: empirically tune the inner loops
of BLAS routines (GEMM, DAXPY, etc.) for the target machine's
cache and register hierarchy; cache the selected configuration
by (machine, BLAS-op) signature; reuse it across every
subsequent matching call. The pattern is four-part: tune once
per machine, cache by signature, reuse across matching
invocations, per-machine scoping. RQ3 inherits the four-part
shape and lifts the signature from op-level to workload-level
(architecture + dataset + loss + grid spec); whether the
pattern's amortization claim survives that signature lift is
the essence of RQ3.
OpenTuner~\cite{ansel2014opentuner} canonized bounded
autotuning search with explicit stopping criteria as the
discipline-level departure from ATLAS-style exhaustive
search; RQ3 inherits an instance of that discipline
(Section~\ref{methods-calibration}).

\subsection{Where this thesis sits}\label{rw-placement}

Prior work supplies the canonical
algorithm~\cite{li2018losslandscape,goldstein_loss_landscape_repo},
the dynamic self-scheduling
primitive~\cite{polychronopoulos1987gss} as the simpler variant
of the StarPU class~\cite{augonnet2011starpu}, the
throughput-ratio applicability
variable~\cite{gallet2021heterogeneous} from a different
workload, the production model-parallel
counterpart~\cite{openvino_hetero}, the
autotune-and-cache pattern~\cite{whaley1998atlas} with
its bounded-search
discipline~\cite{ansel2014opentuner}, and the adjacent
adaptive-sampling direction~\cite{prakash2024adaptive}.

This thesis sits on the task-parallel axis of heterogeneous
execution applied to ML-inference loss-grid; the
model-parallel/pipeline axis is complementary and out of
scope. RQ1 tests whether the
\texttt{functional\_call}+\texttt{vmap} pattern documented for
model ensembling, \texttt{torch.compile} on the
per-grid-point evaluation path, and the composition of the
two transfer to the loss-grid workload pattern — with an
intra-axis composition verdict on whether \texttt{vmap} and
\texttt{torch.compile} multiply, are redundant, or interfere
destructively. RQ2 tests Gallet's throughput-ratio variable in
the ML-inference regime using the simpler dynamic
self-scheduling variant of the StarPU class.

RQ3 adapts the pattern of ATLAS: keeps the tune/cache/reuse flow and
per-machine scope, but changes the unit of reuse from a
BLAS operation to a workload signature
(ML architecture + dataset + loss + grid spec). The cached
artifact is a configuration tuple. We claim
that this workload-level cache amortizes over the
LossLens-scoped session size.

The contribution is
an applicability study on a commodity single-machine (free-tier cloud GPU and consumer laptop), a realistic
deployment surface for interactive
use~\cite{xie2025losslens,losslens_repo}: when do these mechanisms reduce loss-grid runtime,
when do they regress, and how cheaply can the right policy be
chosen at runtime?
