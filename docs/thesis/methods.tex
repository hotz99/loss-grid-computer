\section{METHODS}\label{methods}

This section defines the baseline, the three optimization
approaches mapped to RQ1--RQ3, and the shared measurement and
surface-validation rules. RQ3 asks whether the calibration
routine can be included in a multi-checkpoint comparison session and
still amortize when the selected policy is reused.
Experiment-specific parameters are stated in Section~\ref{experiments}.

\subsection{Canonical Loss-Grid Algorithm
(Baseline)}\label{methods-canonical-algorithm}

We implement the baseline as a sequential GPU-only loop over
the 2D filter-normalized grid of Li et
al.~\cite{li2018losslandscape,goldstein_loss_landscape_repo}.
For grid coordinate $(\alpha,\beta)$ it evaluates
$w(\alpha,\beta)=w_0+\alpha d_1+\beta d_2$ on a fixed data
subset, writes the scalar loss into the surface, and repeats
until the grid is complete. The directions $d_1,d_2$ use the
upstream filter-normalized \texttt{weights} mode.

The baseline is a single-machine GPU-only implementation that
visits grid points sequentially. It excludes MPI, distributed
execution, and CPU helper work. This gives RQ2 a fixed
denominator: the canonical GPU-only path. Per-grid-point
semantics are unchanged; all
comparisons in Section~\ref{results} are relative to this
baseline. A \emph{perturbation} is a single parameter context
$w(\alpha,\beta)$ of a checkpoint; \emph{checkpoint} denotes
a distinct trained model.

\subsection{Algorithm-Level Optimization Candidates
(RQ1)}\label{methods-redesign}

The canonical loop evaluates many perturbed parameter states
against the same data subset. RQ1 tests whether PyTorch's
documented \texttt{functional\_call}+\texttt{vmap}
ensembling pattern~\cite{pytorch_functional_call,pytorch_vmap,pytorch_ensembling}
and \texttt{torch.compile}~\cite{pytorch_compile} apply to
this workload pattern (Table~\ref{tab:opt-map}). These two
candidates match the single-machine constraint. The loss grid
evaluates one model under many parameter states on shared data,
which is the case PyTorch's ensembling pattern
targets~\cite{pytorch_ensembling}, and graph capture is the
relevant kernel-level optimization for a fixed evaluation path. Both
stay within one GPU and add no devices, which keeps the
algorithm-level question (RQ1) separate from the scheduling
question (RQ2).

Each candidate is first compared with
\texttt{vanilla} on $T_{\text{grid}}$. Let $s_v=T_b/T_v$,
$s_c=T_b/T_c$, and $s_{vc}=T_b/T_{vc}$ for
\texttt{vmapped}, \texttt{compiled}, and
\texttt{compiled\_vmapped}. These three baseline-relative
speedups give the per-candidate verdicts. For composition,
the ratio
\[
  q_{\text{compose}} = \frac{s_{vc}}{\max(s_v,s_c)}
\]
compares the composed candidate against the better
individual transform. All four ratios use the CI verdict
taxonomy in Section~\ref{methods-benchmarking}.

\subsubsection{\texorpdfstring{Vectorized Point Evaluation with
\texttt{torch.vmap}}{Vectorized Point Evaluation with torch.vmap}}\label{vectorized-point-evaluation-with-torch.vmap}

\texttt{functional\_call} supplies a perturbed parameter map
to the model without rewriting the module object.
\texttt{vmap} then maps the loss over a leading dimension of
$K$ stacked perturbations, evaluating a chunk of perturbations against
each data batch. Chunking bounds memory; the expected runtime reduction
is dispatch amortization and backend batching, but the result
is backend- and architecture-dependent.

\subsubsection{\texorpdfstring{Graph Capture with
\texttt{torch.compile}}{Graph Capture with torch.compile}}\label{graph-capture-with-torch.compile}

Graph capture is tested in two placements.
\texttt{compiled} wraps the baseline point-evaluation path
with \texttt{torch.compile} while leaving the grid loop
unchanged. \texttt{compiled\_vmapped} applies the same capture
step to the batched evaluator, testing whether it accelerates
or slows vectorized point evaluation on the
loss-grid pattern. Both placements set
\texttt{torch.compile}'s \texttt{fullgraph} parameter, so the
captured region either compiles as one graph or the build
fails. This prevents silent eager fallback inside the
measured region, so a measured speedup reflects fully compiled
execution. PyTorch~2 reports training-time speedups
from this compilation path~\cite{ansel2024pytorch2}; the
loss-grid setting is forward+loss inference with no backward
pass, so whether those gains transfer is an empirical question.

\subsection{Heterogeneous Scheduling
(RQ2)}\label{methods-scheduling}

RQ2 uses a shared-queue self-scheduler. A task is one
grid-point evaluation of the canonical algorithm.
This work is uniform, so the load-imbalance cost of
the chunk-size trade-off (Section~\ref{rw-scheduling}) is
none and chunk size one is used.
CPU and GPU workers poll the queue and claim one grid point
per task. Both devices run the same forward+loss code
and share the baseline surface-validation contract. The CPU/GPU
throughput ratio $r$ is taken as the explanatory variable for
where heterogeneous execution helps. Here $r$ is CPU
forward+loss throughput divided by GPU forward+loss throughput
under the same workload, data subset, and batch policy. RQ2
fixes $p=p_{\max}$ (max available cores) to isolate the throughput-ratio question.
RQ3 treats $p$ as a calibration parameter because session reuse
must select an actual policy.

The \texttt{gpu\_slowdown\_factor} is added latency on the
GPU worker path that artificially tips the achieved CPU/GPU
inference-throughput ratio toward parity when native GPU
throughput is too high.
$r_{\text{native}}$ is $r$ measured without slowdown. The
slowdown is implemented as a sleep on the GPU worker task
path that scales by $s$, where $s=1/r_{\text{native}}$ when
$r_{\text{native}}<1$ and $s=1.0$ otherwise. The
queue-based scheduler sees only task-completion timing, so
the sleep is sufficient at this granularity. Slowed runs
explore controlled CPU/GPU throughput ratios; their speedups
show where adding workers stops helping and are not gains
available on the unslowed machine.

\subsection{Calibration Cache (RQ3)}\label{methods-calibration}

RQ3 measures whether the one-time cost of selecting a CPU/GPU
scheduling policy can be amortized in a multi-checkpoint
session (as in LossLens~\cite{xie2025losslens}). A related checkpoint shares
architecture, dataset, loss, and grid spec, but differs in
learned weights. Under the intended workflow, the calibration
step is unconditional: it runs before the session and may select
either a cached hybrid policy or the GPU-only baseline. If
calibration resolves to GPU-only, heterogeneous compute is not
used and the default path is chosen. The calibration cost is
then useless for that row, so amortization fails. In RQ3,
amortization means the \texttt{cached\_composed} (calibrate
once, reuse the selected policy) session remains faster than
\texttt{vanilla} after calibration time is included.

The GPU-side implementation is controlled by
\texttt{rq3\_config}. This configuration is fixed for
the RQ3 run and is determined by RQ1 for the selected
workload/platform pair. Calibration is conditioned on this
fixed GPU-side configuration because changing GPU-side time changes
the CPU/GPU break-even point.

Calibration selects a scheduling policy tuple
$c=(\pi,b_g,p,b_c)$:
$\pi\in\{\texttt{gpu\_only},\texttt{gpu\_cpu\_hybrid}\}$ is
the placement policy, $b_g$ is the GPU batch size, $p$ is
the CPU worker count, and $b_c$ is the CPU batch size. The
tuple includes $p$ and $b_c$ because CPU forward+loss
throughput is not assumed monotone in worker count or batch
size, so calibration sweeps these axes empirically. All four
fields are swept together; in \texttt{gpu\_only} mode $p$ and
$b_c$ are ignored.

Calibration uses a square probe grid of side $m$, the
smallest integer with $m^2 \ge 4(1+p_{\max})$, where
$p_{\max}$ is the number of CPU cores available to the Python process. The search stops after
\texttt{calibration\_retry}$=P$ consecutive non-improvements.
The selected tuple
is the fastest valid hybrid configuration, or
\texttt{gpu\_only} if no hybrid tuple beats the matched
GPU-only configuration.

Cache reuse runs an empirical tuning step and stores the result in a lookup table with key (machine, architecture, dataset, loss,
grid spec, operating point (native or slowed), \texttt{rq3\_config});
the session tunes once at the start, caches the selected tuple
under this key, reuses it across matching lookups within the
session, and scopes the cached result to the machine.

Amortization is evaluated at the selected RQ3 operating point
with three metrics. \textbf{Session speedup} is
\texttt{vanilla} total time divided by
\texttt{cached\_composed} total time at $N=4$.
\textbf{Break-even $N^{*}$} is
$\lceil\text{calibration\_s}/(T_v-T_p)\rceil$ when
$T_v>T_p$, where $T_v$ is vanilla per-checkpoint time and
$T_p$ is per-checkpoint time under the cached policy after
calibration. It states how many checkpoints amortize the
calibration cost. \textbf{Amortization label} is
\emph{supported} when speedup $>1.0$ and $N^{*}\le 4$,
\emph{supported asymptotically} when speedup $>1.0$ and
$N^{*}>4$, and \emph{refuted} when speedup $\le 1.0$ or
$T_v\le T_p$. Surface failure on any checkpoint suppresses
all three.

\subsection{Benchmarking, Surface Validation, and
Uncertainty}\label{methods-benchmarking}

\textbf{Timing and targets.} Elapsed time is measured at the
call site with \texttt{time.perf\_counter\_ns}; backend
completion is synchronized before stopping the timer.
$T_{\text{grid}}$ measures the wall time to compute one loss
grid after inputs are ready (RQ1/RQ2).
$T_{\text{session}}$ measures a multi-checkpoint session,
including one-time calibration when present (RQ3). Each
$T_{\text{session}}$ value is measured once per (workload,
platform, condition), so RQ3 outcomes are descriptive and not
CI-bounded.
The baseline decomposition
$T_{\text{grid}}=T_{\text{perturb}}+T_{\text{bind}}+
T_{\text{eval}}+T_{\text{collect}}+\text{residual}$ is
computed with the same clock and used only for interpretation.
Only $T_{\text{perturb}}$, $T_{\text{bind}}$, and
$T_{\text{eval}}$ (forward+loss) are timed per grid point;
$T_{\text{collect}}$ and the residual are reported together as
the remainder of $T_{\text{grid}}$.

\textbf{Uncertainty and verdicts.} RQ1 and RQ2 speedup
ratios use paired repeated measurements and effect-size
confidence
intervals~\cite{kalibera2013rigorous,kalibera2020effect}.
Every such ratio $r$ is expressed with values above $1.0$
favoring the candidate. The confidence interval for $r$
gives one of three timing verdicts:
\begin{itemize}\tightlist
  \item \emph{supported improvement}: CI$_{\text{low}}>1.0$;
  \item \emph{supported regression}: CI$_{\text{high}}<1.0$;
  \item \emph{unresolved}: the CI contains $1.0$.
\end{itemize}
RQ3 takes one $T_{\text{session}}$ measurement per
condition, so it does not produce a CI (see amortization-labels in
Section~\ref{methods-calibration}).
\textbf{Pairing and surface validation.} Candidate and baseline
runs are paired by workload, seed, grid, and repeat. A timing
claim is valid when the candidate surface matches the
baseline:
\begin{enumerate}
\item grid-point count and coordinates match the baseline
exactly
\item NaN–NaN pairs at matching coordinates count as equal
\item finite losses are equal under relative tolerance
$1\mathrm{e}{-5}$ with $\text{atol}=0$~\cite{pytorch_allclose};
this is the \texttt{torch.allclose} default relative tolerance
with the absolute term removed, loose enough to cover float32
margin of error and tight enough to detect semantic/visual
divergence
\end{enumerate}
