\section{INTRODUCTION}\label{introduction}

A loss landscape is a 2D
scalar field made by perturbing a trained parameter vector
along two directions and evaluating the loss at each
point~\cite{li2018losslandscape}, supporting
generalization analysis and interactive
model-comparison tools~\cite{xie2025losslens,losslens_repo}.
Computationally, the landscape is represented as an array of
scalar loss evaluations indexed by grid coordinates. Each entry
evaluates the model at the corresponding perturbed parameter
vector on data. One landscape can require hundreds to thousands
of such
evaluations~\cite{li2018losslandscape,goldstein_loss_landscape_repo}.
In interactive checkpoint comparison~\cite{xie2025losslens},
this repeated work can dominate latency on commodity hardware.

The problem is to evaluate candidate single-machine optimization
mechanisms for perturbation-based loss-grid computation under the
constraint of one GPU, the available CPU cores, and finite RAM
and VRAM. The optimization target is the construction of the
loss grid itself: the perturbed model evaluations that fill the
grid. Our thesis explores three mechanisms, each posed as a
research question. The first is single-device evaluation
improvement: \textbf{RQ1. Do PyTorch's stateless evaluation APIs
reduce perturbation-based loss-grid runtime, and for which
architecture types?} The second is heterogeneous CPU+GPU
scheduling: \textbf{RQ2. Does heterogeneous CPU+GPU scheduling
reduce perturbation-based loss-grid runtime, and does the CPU/GPU
throughput ratio determine where it applies across architecture
types?} The third is calibrated policy reuse across checkpoint
sessions: \textbf{RQ3. Can the calibration step be included in a
related checkpoint session and still reduce total session time
when the calibrated policy is reused across checkpoints?}

Because these mechanisms depend on hardware
and workload, the study determines where RQ1 and RQ2 produce
statistically supported runtime reductions, where they regress or
lose practical utility, and whether all measured configurations
preserve the numerical equivalence of the resulting loss surface.
RQ3 then asks whether the one-time calibration cost can be amortized under a multi-checkpoint session.

\subsection{Contributions}\label{contributions}

(RQ1)~An applicability study of PyTorch stateless and
vectorized evaluation primitives
(\texttt{functional\_call}+\texttt{vmap},
\texttt{torch.compile}) for loss-grid construction across
architectures and backends.

(RQ2)~An applicability study of heterogeneous CPU+GPU
scheduling for single-machine loss-grid computation, with
CPU worker count fixed at maximum to isolate the CPU/GPU
inference-throughput ratio as the explanatory variable
across architectures.

(RQ3)~An evaluation of whether a calibrated policy over the
worker-count and batch-size axes that RQ2 holds fixed can be
reused across related checkpoint-comparison sessions to
amortize calibration cost. RQ1 and RQ2 provide the
architecture-dependent evidence; RQ3 inherits a
hybrid-affinity regime from RQ2, native or slowed, where
calibration has an opportunity to change session time.

\subsection{RQ2: Hybrid Scheduling Conditions}\label{rq2-hybrid-scheduling-conditions}

\begin{itemize}\tightlist
  \item explanatory variable: the CPU/GPU forward+loss
    inference-throughput ratio. Forward+loss inference
    dominates grid runtime (\ref{tab:profile}), so
    inference throughput ratio is the relevant narrowing of
    the general CPU/GPU throughput ratio
    (\ref{rw-placement}).
  \item expected ratio threshold: near or above parity, hybrid
    scheduling absorbs useful CPU work; far below parity,
    GPU-only is expected to dominate or
    leave the verdict unresolved
    % TODO cite: experiment verdict framing
  \item workload dependence: sequential row-gru should
    require less artificial GPU slowdown to approach
    inference parity than cifar10 resnet20; nvidia's
    DL perf guide for CNNs ~\cite{nvidia_cudnn_convolution_guide} describes
    tensor-shape and alignment conditions under which
    conv kernels reach high GPU throughput;
    resnet20 forward path is dominated by 2d conv
    layers that meet those conditions; rowgrud
    is a recurrent sequence of matrixvector
    ops with dependence between steps; hence expect resnet20h above
    rowgru on GPU
    % TODO cite: recurrent/time-dependence claim if kept
  \item platform interpretation: on a discrete-memory
    CPU/GPU system, CPU compute reads and writes host DRAM and
    contends with the GPU only at the PCIe bus, on host-device
    transfers. On a unified-memory system (Apple M4), CPU and
    GPU share one physical memory pool and one memory bus by
    design, so any concurrent CPU compute competes with the
    GPU for memory bandwidth regardless of transfers; expect hybrid scheduling to tolerate concurrent
    CPU workers more on the discrete-memory machine than on unified-memory
    % TODO cite: slowdown instrument scope and platform specs
\end{itemize}

\subsection{RQ3: Calibration and Cache Reuse}\label{rq3-calibration-and-cache-reuse}

\begin{itemize}\tightlist
  \item measurement scope: single-measurement ratios are descriptive;
    CI based cross-session repeatability not measured
  \item cache point: calibration runs once at start; reuse only matters
    if per-checkpoint saved time amortizes one-time calibration cost
  \item negative case: if calibration resolves gpu-only then cache has
    no useful policy to reuse; report amortization refuted for that case
\end{itemize}

\subsection{Hardware Dependence and Limits}\label{hardware-dependence-and-limits}

\begin{itemize}\tightlist
  \item scoped to unified-memory consumer hardware and
    discrete vram free-tier cloud hardware
  \item four workloads span mostly orthogonal ML
    families but do not support claims beyond our workload set
  \item expected dependence axes: memory pressure for large vmap
    chunks, backend-specific handling of the transformed tensor
    program, scheduler overhead at small grid-task granularities, and
    platform-specific numerical behavior at surface validation
    % TODO cite: measured diagnostics where each axis appears
  \item observed differences should link to platform arch differences
\end{itemize}
